Our actual project

What can we search today?

Registration

name, email, and date_of_birth are useful for customer search. The password field is not.

Bill

bill_id, bill_status, bill_amount, created_at, and customer_id support precise filters.

The JWT-protected /account/api/registrations/ endpoint lists customers, but has no search configuration. The customer page has a visual search box that does nothing yet. There is no Bill API in the router.

3
Why we need it

The current API makes the client search the whole list

Imagine 50,000 customers and a user trying to find Rahim Ahmed. Today the Registration API returns the normal list even if the client sends ?search=rahim. The client must download or page through many records and search them itself.

User asks for Rahim
→
Server returns all
→
Client searches
Our target: the server finds matching customers first, then sends a small, useful JSON result.

A Django HTML view can also filter data. We teach the API form because this class already uses DRF and JSON clients.

4
Core idea

A search API is a list API with a question

A client sends a GET request with a search term. The server returns matching records as JSON.

GET /account/api/registrations/?search=rahim

The path chooses the Registration collection. search=rahim asks for customers whose allowed text fields match “rahim”. The same endpoint can still return the full list when no search term is supplied.

Current behavior: this ViewSet ignores search, so the example URL still returns the normal list.
5
How it is used

From the customer search box to matching JSON

Type “rahim”
→

→
DRF filters
→
Show results

The browser can send GET /account/api/registrations/?search=rahim with its access token. The ViewSet filters the allowed records, the serializer returns JSON, and the page displays the matching names. The current visual search box must be connected to this flow.

Proposed response after safe pagination:
{ "count": 1, "results": [
  { "id": 1, "name": "Rahim Ahmed", "email": "rahim@example.com" }
] }

This is a shortened target response. It is not the current API output.

6
Production-grade basics

A small implementation can still be credible

Correct matches

Search only allowed fields. Exact email and date filters follow clear rules. Invalid input gets an error.

Safe access

Keep JWT permission. Do not search or return passwords or secret bill codes.

Predictable results

Use stable ordering and pagination. Test a match, no match, invalid input, and no token.

Measure slow queries before choosing an index. These basics teach how a product endpoint is built without needing a separate search engine.

7
Read a URL

The question mark and ampersand

/account/api/registrations/?search=rah&born_from=1990-01-01

? begins the query

Everything before it identifies the API resource. Everything after it gives optional choices.

& adds another choice

The request carries both a text search and a birth-date filter. We will define how those conditions combine.

This is a proposed request format. Query parameter names are part of the API design we will choose before coding.

9
Three different jobs

Search, filter, and ordering

Search

Which customer names contain rah?

Filter

Which customers were born before 2000?

Ordering

Should the matching customers appear by name or ID?

Search and filters decide which records remain. Ordering only arranges those records. Pagination can then show one manageable page.

10
Text search 1

Contains: find text anywhere in a name

Planned request: ?search=rah

If we search names with a case-insensitive contains rule, all three sample customers match: Rahim Ahmed, Rahat Islam, and Ayesha Rahman.

The user does not need to remember the complete name or whether “rah” begins the first name or surname.

DRF SearchFilter uses case-insensitive contains matching by default when configured for text fields.

11
Text search 2

Starts with: narrow the name list

Search names that start with: rah

Rahim Ahmed and Rahat Islam match because their names begin with “rah”. Ayesha Rahman does not match this rule because her complete name begins with “Ayesha”.

A prefix rule is useful when the user knows the beginning of the name. It answers a different question from “contains”.
12
Text search 3

Exact email: identify one customer

Planned request: ?email=rahim@example.com

The complete email should match Rahim Ahmed only. An email address is a specific identifier. If one character is wrong, the API should not guess which customer to edit or bill.

This is a field filter with an exact rule. It is different from a general ?search= term that checks several text fields.
13
DRF search tool

What does SearchFilter provide?

DRF has a built-in SearchFilter. After we configure it on the Registration ViewSet and name the allowed fields, it can read a single search query parameter and match text in those fields.

It can do

Case-insensitive partial matches by default. It can also use configured starts-with or exact lookups.

It does not do automatically

Typo correction, exact-first relevance ranking, date ranges, or amount ranges.

We will choose name and email deliberately; sensitive fields do not belong in search.

14
Customer filters

Filter by an exact date or a range

Exact date

?date_of_birth=1996-04-12

From our sample table, Rahim is the only match.

Date range

?born_from=1990-01-01
&born_to=1999-12-31

Rahim and Ayesha match. Rahat was born in 2000.

Before implementation, we must decide whether range boundaries are included and what response an invalid date should produce.

Combine rules

Search OR across fields; filter AND by date

?search=rah&born_from=1990-01-01&born_to=1999-12-31

The general text search may check name OR email. The date range then applies as an AND condition: a customer must match the text and be born in the range.

18
Result behavior

What if the request has no useful result?

No match

Return an empty list. The interface can say “No customers found.”

Bad value

Explain an invalid date or amount. Do not silently ignore the filter.

Blank search

Choose a consistent rule: show all permitted records or show none.

These decisions are part of the API contract. Students should know the expected response before writing the queryset code.

19
Data protection

Search must follow the API’s access rules

The Registration API already requires a valid JWT access token. Adding a search parameter must not expose records to someone who could not use the list endpoint.

We must allow only intended fields. Registration.password and Bill.bill_code are not search fields. The current serializer also returns the password field; that separate security issue needs correction before production use.

A search result should make it easier to find a permitted record, not reveal a sensitive field.
20
Practical scale

Many results, sorting, and the current cache

If thousands of customers match “a”, returning all of them is difficult to use. A stable sort order and pagination give the client a predictable first page and a way to request more.

The HTML customer page currently caches one unfiltered list under customer_list. Its search box needs a query-aware design when connected. The DRF Registration API does not automatically use that HTML-page cache.

Search correctness comes first: each query must return its own matching records.

Our CRM problem

What if every request asks the database?

Imagine 1,000 users opening the same customer list at the same time.

User 1
→
Database
  
User 2
→
Database
  
...

The database repeats the same work again and again.

Simple classroom assumption: one customer-list query needs 10 ms of database time. The database can safely complete about 100 such queries per second.

Users arrive togetherRepeated database readsApprox. time to finish them all
1 user1 query10 ms
1,000 users1,000 queries1,000 ÷ 100/sec = 10 seconds
10,000 users10,000 queries10,000 ÷ 100/sec = 100 seconds

Later requests wait in a queue. In a real system, heavy pressure can make the time even worse.

3
Meaning

What is cache?

Cache is a temporary, fast copy of data that we may need again soon.

Temporary

It can expire or be removed.

Fast

Usually quicker than asking the database.

A copy

The main data still belongs in the database.

Everyday idea

Desk versus library

Without cache

Each time you need one book, walk to the library and find it.

With cache

Keep today’s most-used book on your desk for quick access.

The library is like the database. Your desk is like the cache.

7
Basic structure

Cache usually uses a key and a value

Key:   "customer_list"
Value: [customer data]

Key

A unique label used to find cached data.

Value

The saved data: text, number, image, JSON, or more.

Example: A user asks, “Show me the customer list.” Django uses the key customer_list to ask cache.

User asks for
customer list
→
Django asks for key:
customer_list
→
Cache finds the
same key
→
Returns its value:
customer data
= cache hit

The key finds the data. The connected value is what cache returns.

Two possible results

Cache hit and cache miss

Cache hit ✓

Data is found in cache.
Return it quickly.

Cache miss ✗

Data is not in cache.
Ask the database.

Cache miss
→

Important word

TTL: Time To Live

TTL tells cache how long it may keep a value.

customer_list  ->  keep for 60 seconds
Save at 10:00
→
Available until 10:01
→
Expired

After expiry, Django gets fresh data from the database again.

10
Where it lives

How is cache stored?

Memory / RAM

Very fast. Common for application cache.

Disk

Can store more, but is usually slower than RAM.

Near the user

A browser or CDN may store files close to the user.

How much space? There is no one “typical” size. The developer sets a limit. For our classroom example, imagine a 100 MB memory cache.

Limit:
100 MB
→
Save data:
40 MB used
→
More data:
95 MB used
→
Full:
may remove old values

Used cache space does go up when we save values. It goes down when values expire (TTL), are deleted, or are removed to make space. The exact full-cache rule depends on the cache. The limit stays 100 MB until we change it.

Types: where it lives

Cache can exist in different places

TypeLocationSimple example
Browser cacheUser's browserLogo image already downloaded
CDN cacheServers near usersWebsite image or video
Application cacheWith/near DjangoCustomer list or dashboard total
Database cacheDatabase systemFrequently read query data

CDN = Content Delivery Network. It is a network of servers that delivers files, such as images and videos, from a server close to the user.

Real-world connection:

Netflix = CDN cache

When you press Play, Netflix can stream video from a suitable nearby/ISP server that already stores a copy.

12
Types: what it stores

Cache can store many kinds of data

Words & numbers

Customer name, product price, dashboard count.

JSON / API response

A customer list returned by an API.

Images & files

Profile image, CSS, JavaScript, PDF, or video.

So “cache type” can mean where it lives or what data it stores.

Examples as cache entries (key → value):

customer_42_name
→ Rahim

customer_42
→ {"id": 42, "name": "Rahim"}

customer_42_profile_image
→ Rahim's profile image file

13
Why use it?

Cache helps the whole system

Faster

Users get common data sooner.

Less database work

Fewer repeated queries.

More users

The system can handle more repeated reads.

Cache is especially useful for data that is read often but changes less often.

14
System design

Cache protects the database during heavy traffic

Many users
→
One cached copy
→
Fast replies

Without cache

Many repeated reads reach the database.

With cache

Many reads can use the same cached value.

15
Real example

How Facebook used cache while scaling

Facebook began using Memcached in 2005 because database queries on every page load were making pages slower.

The idea

Keep frequently requested data in fast memory instead of repeatedly asking the database.

The result

Cache became an important part of handling huge numbers of requests as Facebook grew.

Simple illustration (not Facebook's exact code): Many people open the same popular profile or post.

First request
→
Cache miss:
ask database
→
Save a copy in
Memcached
→
Later requests:
cache hit

Source: Meta Engineering, “Scaling memcache at Facebook,” 2013 — engineering.fb.com/2013/04/15/core-infra/scaling-memcache-at-facebook/

16
Important rule

Cache is not the main database

Database = official record

Keep the important, permanent customer and bill data here.

Cache = fast temporary copy

May expire, be cleared, or sometimes contain older data.

If cache disappears, the application should still work by reading the database.

17
Be careful

Cache has trade-offs

Old data

A cached value may not show a recent update.

Memory limit

We cannot save everything forever.

Extra thinking

We must decide when to refresh or remove it.

The right question is: what is safe and useful to cache?

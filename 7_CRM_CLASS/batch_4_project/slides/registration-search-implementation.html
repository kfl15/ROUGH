Why extend the list API?

Lesson step 3 of 25

Show: Before this change, GET /account/api/registrations/ returned the list, but adding ?search=Teacher did not make the ViewSet search. Knowing an ID allowed a detail lookup; it did not help someone who knew only a name or email.

GET /account/api/registrations/2/           -> customer with ID 2
GET /account/api/registrations/?search=Teacher -> customers matching Teacher
Teacher explanation

Both requests use the route that already exists. The first selects one known ID. The second searches the collection using a query parameter. Search happens in Django/database code before the response is serialized and sent to the client. This can reduce how many rows the client receives. DRF's default partial search is not automatically fast on a large database; indexes and query measurement would be separate scaling work.

What happens inside the request?

Lesson step 5 of 25

Show:

GET URL + Bearer token
  -> JWT authentication checks the token
  -> get_queryset() applies exact email and DOB bounds
  -> SearchFilter applies ?search=
  -> OrderingFilter chooses the order
  -> pagination selects the requested page
  -> RegistrationSerializer builds the JSON without password
Teacher explanation

The features work together. A customer must pass each requested structured filter and the text search. Ordering arranges those matches, and pagination sends only one part of them. The serializer controls what each returned customer looks like. If authentication fails, the request stops with 401 before customers are returned.

Text search with DRF `SearchFilter`

Lesson step 8 of 25

Show the code in RegistrationViewSet:

filter_backends = [SearchFilter, OrderingFilter]
search_fields = ['name', 'email']
Teacher explanation

SearchFilter reads the search query parameter. search_fields allows it to check only the Registration name and email fields. With the current DRF default, matching is case-insensitive and partial. A record may match in either field. A password is never a searchable field. If SearchFilter were absent, ?search=Teacher would not change the list.

Live example: GET /account/api/registrations/?search=Teacher returned one result: Teacher Test, ID 2. A lowercase teacher would match it too.

Exact email is a different rule

Lesson step 9 of 25

Show the first part of get_queryset():

def get_queryset(self):
    queryset = super().get_queryset()
    email = self.request.query_params.get('email')

    if email:
        queryset = queryset.filter(email__iexact=email)
Teacher explanation

super().get_queryset() starts with the Registration records configured on the ViewSet. query_params.get('email') reads ?email= from the URL. If it was supplied, email__iexact keeps only a whole email match while ignoring letter case. This is useful when the caller knows a particular customer's full email. If no email parameter is supplied, this part leaves the queryset alone.

Date filters read text from the URL

Lesson step 10 of 25

Show:

from_text = self.request.query_params.get('dob_from')
to_text = self.request.query_params.get('dob_to')

try:
    from_date = parse_date(from_text) if from_text else None
    to_date = parse_date(to_text) if to_text else None
except ValueError:
    raise ValidationError({'date': 'Use YYYY-MM-DD for dob_from and dob_to.'})
Teacher explanation

A URL contains text, even when that text looks like a date. parse_date() turns the supplied text into date values that Django can compare. Either bound is optional. If the supplied text cannot represent a valid calendar date, the API returns a 400 error with a useful message. These checks validate the search input; they do not validate a customer's saved date of birth when a customer is created.

Example: dob_from=banana is an invalid filter value. A saved customer DOB such as 2027-02-01 is a different piece of data; this search code does not decide whether it is a realistic DOB.

Date range errors and inclusive bounds

Lesson step 11 of 25

Show the remaining date logic:

if (from_text and from_date is None) or (to_text and to_date is None):
    raise ValidationError({'date': 'Use YYYY-MM-DD for dob_from and dob_to.'})

if from_date and to_date and from_date > to_date:
    raise ValidationError({'date': 'dob_from must be before or equal to dob_to.'})

if from_date:
    queryset = queryset.filter(date_of_birth__gte=from_date)
if to_date:
    queryset = queryset.filter(date_of_birth__lte=to_date)

return queryset
Teacher explanation

The first check catches date text the parser could not understand. The second rejects a start after the end. gte means on or after; lte means on or before. The boundaries themselves are included. A customer with a null DOB does not match a date range. The final return queryset hands the narrowed records back to DRF.

Live example: ?dob_from=2026-09-01&dob_to=2026-09-30 returned three records, including customers born on September 1 and September 30.

Ordering the matches

Lesson step 13 of 25

Show:

filter_backends = [SearchFilter, OrderingFilter]
ordering = ['id']
ordering_fields = ['id', 'name', 'email', 'date_of_birth']
Teacher explanation

OrderingFilter reads ?ordering=. The ordering_fields list limits the fields a client may use. If no ordering parameter is sent, the ViewSet orders by ID. A leading minus sign means descending order. Ordering matters especially with pagination: page 1 and page 2 need a predictable sequence. For the classroom demo, -id avoids ambiguity from records with missing DOBs.

Live example: ?ordering=-id&page_size=3&page=1 showed IDs 14, 13, and 10 first. Without the minus sign, lower IDs come first.

Pagination: one page of results

Lesson step 14 of 25

Show:

class RegistrationPagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = 'page_size'
    max_page_size = 50

class RegistrationViewSet(viewsets.ModelViewSet):
    pagination_class = RegistrationPagination
Teacher explanation

The default page holds ten records. A client may request a different page size with page_size, but no more than 50. page selects which page to read. pagination_class connects these rules to this ViewSet. Pagination applies after filtering and ordering, so count is the total number of matches, not just the number on the current page.

Live example: With nine matching customers, ?page_size=3&page=2 gives count: 9, three items in results, and non-null previous and next links.
